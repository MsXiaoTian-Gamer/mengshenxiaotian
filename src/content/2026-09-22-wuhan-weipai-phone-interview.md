## 技术问题复盘

### 1. UGUI：无限背包为什么用 Mesh 还是 RectMask2D

考的是 UGUI 底层机制 + 实际项目里"无限背包/无限列表"的实现选型。

我答的是 **Mesh 方案**：直接合批绘制，理由是**性能开销小**——不走 GameObject / UI 组件的开销，draw call 和内存占用都低，适合格子数量大的列表场景。

事后复盘，其实可以再补一条对比：纯 UGUI 路线是 **RectMask2D + 对象池复用**——只实例化可视区域内的 item，滚动时复用对象池，用 RectMask2D 做矩形裁剪，不破坏合批，开发效率和交互便利性更好（点击、布局都能直接用）。两者的本质权衡是开发效率与交互便利（RectMask2D + 复用）vs 极致渲染性能（Mesh 合批）。这个对比当时没展开讲，下次可以主动带上。

顺带补一个知识点：**Mask vs RectMask2D** 的区别——Mask 基于模板缓冲（Stencil），会破坏合批、可能引入额外 draw call；RectMask2D 是纯矩形裁剪，不做模板测试，不破坏合批，性能更好。

**追问：如果你想弹窗弄到最前面怎么办**

我答的是**在 Inspector 里的操作**：同一 Canvas 下把弹窗节点在层级面板中拖到最上面（后绘制的覆盖先绘制），或者在 Inspector 里调 Canvas 的 Sorting Order，让弹窗所在的 Canvas 排到最前。

事后想想还可以补代码层面的方案：运行时用 `transform.SetAsLastSibling()` 动态置顶、多 Canvas 场景统一由 UI 框架管理 panel 栈、弹窗入栈自动置顶。当时只答了 Inspector 的手工操作，也算答到了点上，但可以说得更全。

### 2. 对象池

- **动机**：频繁创建销毁对象会产生 GC 压力，尤其子弹、特效、飘字这类高频短生命周期对象。
- **核心实现**：栈/队列 + 预分配 + 复用；关键 API 是 `OnEnable` 做初始化、`OnDisable` 做还原，避免"脏数据泄漏"到下一次复用。
- **进阶点**：池的扩容策略、场景切换时的清空策略；热路径对象避免装箱（用泛型池而不是 object 池）。

**追问：可不可以直接开很大的容量？**

这个问题我当时没想出来。面试官点了一句：**如果一共就 2 个怪物，你开 10000 个实例留在对象池里**——恍然大悟。

对象池的容量不是越大越好，预分配的内存是实打实占着的。容量应该跟**实际并发峰值**匹配：先预估同一时刻最多同时存活的实例数，池子略大于这个峰值即可；多了是纯浪费内存，少了才需要走扩容或临时 new。合理做法是"预分配一个合理初值 + 按需扩容 + 上限封顶"，而不是无脑开大。

### 3. 策略模式

- 本质：把一组可互换的算法封装成独立策略类，运行时替换行为，符合开闭原则。
- 结合项目答的：行为树里不同节点的决策逻辑、技能系统里不同伤害结算方式都可以用策略模式组织，避免一大坨 if-else。
- 补充了和状态模式的区别：状态模式是"对象自身状态迁移"，策略模式是"外部注入行为"，两者关注点不同。

### 4. 观察者模式

这题我**答岔了**——当时脑子里想的全是单例模式，把观察者模式答成了单例（全局唯一实例、全局访问点），面试官应该是看出来了。事后复盘把两者彻底理清：

- **观察者模式**：一对多依赖——主题（Subject）状态变化时，自动通知所有注册的观察者（Observer），实现发布-订阅式的解耦。
- **单例模式**：保证一个类只有一个实例，提供全局访问点，如 `GameManager.Instance`。
- 两者完全不同：单例管"实例唯一性"，观察者管"状态变化通知"。虽然项目里常把事件中心做成单例，但那是"单例 + 观察者"的组合使用，不能混为一谈。
- **观察者在 Unity / C# 里的落地**：`event` / `delegate`、`UnityEvent`、以及自研的事件中心（EventManager / 全局事件总线）。MVC 里"数据变化通知 View 刷新"就是典型的观察者应用。
- **关键点**：注册了一定要记得注销——不然对象被事件引用住无法回收，造成内存泄漏和"幽灵回调"；事件的执行顺序、异常隔离（一个观察者抛异常不能拖垮整条通知链）也是工程上要处理的细节。

这个答错值得记一笔：设计模式之间容易记混，平时要把易混淆的模式放一起对比记忆，而不是单个背定义。

### 5. 行为树

这块聊得很浅，基本一句话带过——介绍了节点类型（组合节点 Sequence / Selector、装饰节点、叶节点）、`Tick` 驱动、节点返回 Success / Failure / Running 三态，然后就过了，没有深挖。

我自己在行为树这块其实有不少能讲的（比如 AI 管理器如何驱动行为树、和 FSM 的对比），但当时没主动往深处引。算是这场面试里一个小小的遗憾——**熟悉的话题没有抓住机会展开**。

### 6. 分辨率适配

- **核心思路**：`CanvasScaler` 的 Scale With Screen Size 模式 + 参考分辨率（如 1080×1920），再配合 `RectTransform` 锚点做自适应。
- **多分辨率策略**：竖屏游戏按宽度/高度适配的选择逻辑；`SafeArea` 适配刘海屏和全面屏；不同宽高比下的 UI 布局兜底（背景拉伸 / 裁切 / 加黑边）。
- **进阶**：字体大小自适应、图文混排的适配。

### 7. MVC

- **理论**：Model（数据 / 逻辑）、View（表现）、Controller（输入 / 调度）三层分离，职责单一、可测试性好。
- **实际落地**：在 Unity 里聊了 MVP / MVVM 的变体，以及 UI 框架里常用的"数据驱动 UI"思路——数据变化通过事件通知 View 刷新，而不是 View 主动拉取。

### 8. 算法：BFS / DFS / Prim / A*

算法部分连着问了四个。其中 BFS / DFS 问的是**用的什么数据结构**，这块我答得很好：

- **BFS**：核心数据结构是**队列（Queue）**。按层遍历，出队一个节点、把未访问的邻居入队，配合 visited 标记避免重复访问；无权图最短路径的经典解法。
- **DFS**：核心数据结构是**栈（Stack）**——显式用栈实现迭代，或者用递归（系统调用栈天然就是栈）。适合连通性检测、拓扑排序、迷宫生成。

答完 BFS / DFS 后，面试官追问：**A\* 和 BFS 像还是和 DFS 像？**

我答的是：**A\* 像 BFS，并加了启发式搜索**——数据结构上 BFS 用队列、A* 用优先队列按 `f = g + h` 扩展，本质都是"从起点向外按层/按优先级扩展"的框架，区别就是 A* 用启发函数 `h` 引导方向；DFS 是沿分支扎到底再回溯，跟 A* 不像。

事后复盘这个回答其实可以再展开成三层理由，答得更完整：

1. **数据结构上**：BFS 用队列维护"待扩展的前沿集合"，A* 用优先队列（堆）维护同一套前沿集合，扩展顺序按 `f = g + h` 排序——两者都是"从起点向外逐层/逐优先级扩展"的框架，而 DFS 是沿着一条分支扎到底再回溯。
2. **最优性上**：BFS 在无权图上保证最短路径，A* 在启发函数一致（admissible + consistent）时也保证最优解；DFS 不保证。
3. **区别在启发式**：A* 用 `h` 引导扩展方向，会优先朝目标方向深入——这一点吸收了 DFS"有方向地深入"的直觉，但不会像 DFS 那样一条路走到黑，本质还是 BFS 那种"按优先级全面扩展"的体系。

一句话总结：**A\* = BFS（Dijkstra）的加权推广 + 启发式引导**，从框架上更接近 BFS，从行为倾向上带一点 DFS 的"方向性"。核心判断当时答对了，理由展开下次可以更充分。

- **Prim**：最小生成树算法，贪心策略，从任意节点开始不断扩展最小权值边；用优先队列（堆）优化取最小边的过程，复杂度 O(E log V)。
- **A\***：启发式搜索，`f = g + h`，开放列表 + 关闭列表；`h` 的选取（曼哈顿距离 / 欧氏距离 / 对角线距离）直接影响搜索效率。

### 9. 协程

- **本质**：协程不是多线程，它是基于迭代器（`IEnumerator`）的"挂起 / 恢复"机制，跑在 Unity 主线程上。
- **关键点**：`yield return null`（下一帧）、`yield return new WaitForSeconds()`（基于时间）、`yield return new WaitUntil()`（条件）；`StartCoroutine` / `StopCoroutine` 的控制。
- **坑**：协程不随 `SetActive(false)` 自动停止，要配合 `OnDisable` 处理；大量协程要注意性能；和 `async/await`、`UniTask` 的对比——UniTask 零分配、可返回结果，新项目我更倾向 UniTask 而不是裸协程。

### 10. JSON 新旧版本怎么区分

不是泛泛问"什么是 JSON"，而是问**协议/存档迭代时，新旧版本的 JSON 数据怎么区分兼容**。我答了几个层面：

- **加版本号字段**：数据结构里带 `version` 字段，读取时先读版本号再走对应的解析/迁移逻辑，这是最直接的区分手段。
- **向后兼容**：新版本只做"加字段"时，旧数据缺字段要能给默认值；用"忽略未知字段"的策略保证新客户端能读旧数据、旧客户端（如果有）不因多余字段崩溃。
- **版本迁移**：跨大版本时写迁移函数链（v1 → v2 → v3 逐级升级），而不是一把梭；迁移要幂等、可回滚验证。
- **实践**：Unity 里用 `JsonUtility` 的话版本字段要手动管理；用 `Newtonsoft.Json` 可以配合 `MissingMemberHandling`、自定义 `JsonConverter` 处理版本差异；配置表类数据一般不走 JSON 版本这套，用增量更新 + 校验。

### 11. 开放题：如果你想重构项目，你认为最大的阻碍是什么

我说的是：**对 AI 行为树和 AI Manager 的解耦**。

理由是：我自己项目里写的 `aimanager` 耦合很严重——行为树执行依赖 Manager 的驱动逻辑，节点和 Manager 绑得比较死，导致节点难以独立测试和复用，想换驱动模型时牵一发动全身。重构的阻碍不在"改行为树本身"，而在**解耦带来的连锁改动**：Manager 的对外接口、节点的生命周期、编辑器工具、以及依赖 Manager 状态的周边模块全都要跟着调整，回归成本高。

面试官对这个回答反馈不错，因为这是从真实项目里挖出来的、有具体痛点的答案，而不是背出来的八股。

## 手撕算法：斐波那契

最后现场手写斐波那契。我用 **vector 数组**做的——开一个 `vector` 存前两项，然后循环递推填充，返回第 n 项：

```cpp
// vector 数组版本（O(n) 时间 O(n) 空间）
int fib(int n) {
    if (n <= 1) return n;
    std::vector<int> dp(n + 1);
    dp[0] = 0;
    dp[1] = 1;
    for (int i = 2; i <= n; ++i) {
        dp[i] = dp[i - 1] + dp[i - 2];
    }
    return dp[n];
}
```

这就是 DP（动态规划）的入门形态：自底向上填表。事后想想可以补一句优化——其实只需要保留前两个值，滚动数组可以把空间压到 O(1)，以及递归版会爆栈、矩阵快速幂能到 O(log n)、大数溢出要换 long / BigInteger。当时没展开，但解法本身是稳的。

## 总结与反思

### 做得好的地方

- **BFS / DFS / A\*** 答得不错：BFS / DFS 的数据结构（队列/栈）答得干脆，被追问"A* 像 BFS 还是 DFS"时核心判断准确（像 BFS + 启发式搜索）。
- **开放题**回答都来自真实项目经验，有具体场景和思考过程（AI Manager 解耦、MagicCloth），不是背答案。
- **手撕算法**写得稳，vector 数组 DP 解法本身没问题。
- 反问环节拿到了关键信息：有导师 1 对 1 带、面试官对简历写法的建议。
### 可以改进的地方
- **观察者模式答成了单例模式**——两个模式记混了，面试现场直接暴露。设计模式要对比记忆（单例管实例唯一性，观察者管状态通知），不能单个背定义。
- **对象池容量追问没答出来**——"容量要和实际峰值匹配，不是越大越好"这个点当时没转过弯，被面试官举例点醒。这类贴近工程实际的追问，平时得多想想"为什么"。
- **行为树聊得太浅**——自己明明在这块有较深的实践，却没有主动把话题引向自己熟悉的方向，错过了展示深度的机会。
- **UGUI 无限背包**只答了 Mesh 一种方案，没有展开 RectMask2D + 对象池的对比；**弹窗置顶**也只答了 Inspector 的手工操作（拖节点 / 调 Sorting Order），代码层的方案（SetAsLastSibling、UI 框架管理）可以补上。
**一点心得**
微派这面给我的感觉是：**不追求偏题怪题，但很在意你是不是真的做过、真的思考过**。UGUI、对象池、策略模式、行为树、MVC 全是游戏开发日常——而这些恰好都是我在自己项目和实习里真实做过的东西：行为树和 AI 驱动的底气，来自我自己的行为树项目与教学 Demo，对象池、UI 适配来自独立游戏开发，策略模式来自技能/决策系统的设计。开放题更是直接考察项目经验和架构意识。这种面试风格对"有真实项目、有独立思考"的候选人很友好，前提是**别让这些经验只躺在简历里，面试时要主动讲出来**——行为树那题我就吃了没展开的亏。

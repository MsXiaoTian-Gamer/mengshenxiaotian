# Unity 第三阶段：项目架构与工程化实践学习笔记

这份笔记适合已经完成第二阶段，能够独立写出单个系统，但开始遇到这些问题的人：

- 脚本越来越多，关系越来越乱
- 功能能跑，但不好维护
- 数据、UI、逻辑混在一起
- 场景切换、存档、资源加载开始变复杂
- 想继续加内容，但每次改动都容易牵一发动全身

第三阶段的重点不是再背更多模式名字，而是学会：

- 怎么把一个 Unity 项目搭成清楚的架构
- 怎么把配置、运行时数据、存档数据分开
- 怎么让场景流程、UI、资源、存档各自负责自己的事
- 怎么让项目能持续迭代，而不是写到一半就乱掉
- 怎么通过工具和规范降低重复劳动

核心目标：

> 从“能把功能写出来”，进步到“能把项目做成长期可维护的工程”。

---

## 一、第三阶段应该优先学什么

建议优先掌握这些内容：

1. 项目架构和分层
2. `ScriptableObject` 数据驱动
3. 场景流程和异步加载
4. 存档和进度系统
5. UI 架构和数据绑定
6. 资源管理和引用集中
7. 性能分析和基础优化
8. 编辑器工具和自动化

不建议一开始就冲这些很重的内容：

- 完整的依赖注入框架
- ECS / DOTS

- 自研复杂资源管线
- 过度抽象的通用框架

这些不是不能学，而是第三阶段先把“项目基本功”打扎实更重要。

## 二、项目架构：先把边界划清楚

第三阶段最重要的一件事，是先决定“每一类代码负责什么”。

常见的清晰拆法是：

```text
Scripts/
  Bootstrap/
  Core/
  Data/
  Domain/
  Gameplay/
  Services/
  UI/
  Editor/
  Tests/
```

可以这样理解：

- `Bootstrap` 负责启动和组装
- `Core` 负责全局基础能力
- `Data` 负责配置数据
- `Domain` 负责运行时规则和纯数据
- `Gameplay` 负责具体玩法
- `Services` 负责存档、场景、音频等服务
- `UI` 负责界面展示
- `Editor` 负责编辑器工具

最重要的原则是：

> 配置数据、运行时数据、持久化数据尽量不要混在一起。

### 三类数据要分开

1. 配置数据：放在 `ScriptableObject` 里，方便调参
2. 运行时数据：放在普通 C# 类里，表示这一局游戏里的状态
3. 持久化数据：放在存档结构里，表示需要写入磁盘的内容

### 示例：配置、运行时状态、启动器

```csharp
using System;
using UnityEngine;

// 游戏配置，只存放开局前可调整的静态参数
[CreateAssetMenu(menuName = "Game/Game Config")]
public class GameConfig : ScriptableObject
{
    public int startHealth = 100;
    public int startCoin = 0;
    public string firstSceneName = "Main";
}

// 运行时状态，只存放这一局游戏中的动态数据
public class GameState
{
    public event Action<int> OnCoinChanged;
    public event Action<int> OnHealthChanged;

    public int Coin { get; private set; }
    public int Health { get; private set; }

    public GameState(GameConfig config)
    {
        Coin = config.startCoin;
        Health = config.startHealth;
    }

    public void AddCoin(int amount)
    {
        if (amount <= 0)
        {
            return;
        }

        Coin += amount;
        OnCoinChanged?.Invoke(Coin);
    }

    public void SetHealth(int value)
    {
        Health = Mathf.Max(0, value);
        OnHealthChanged?.Invoke(Health);
    }
}

// 启动器只负责组装对象，不负责业务规则
public class GameBootstrapper : MonoBehaviour
{
    [SerializeField] private GameConfig gameConfig;
    [SerializeField] private PlayerController playerController;
    [SerializeField] private CoinView coinView;

    private GameState gameState;

    private void Awake()
    {
        // 统一在这里创建运行时状态，避免各处自己 new 一份
        gameState = new GameState(gameConfig);
        playerController.Initialize(gameState);
        coinView.Bind(gameState);
    }
}
```

### 这一段要记住的判断标准

- 想调数值，就放 `ScriptableObject`
- 想表示当前这一局的变化，就放运行时类
- 想跨进程保存，就放存档结构
- 想把系统组起来，就放启动器

### 练习要求

做一个最小的项目骨架：

- 一个 `GameConfig`
- 一个 `GameState`
- 一个 `GameBootstrapper`
- 不要在很多脚本里自己去找对象
- 不要把配置和运行时状态写到同一个类里

## 三、`ScriptableObject`：把配置从逻辑里拿出去

第二阶段已经接触过设计模式，第三阶段开始要把“配置驱动”真正用起来。

`ScriptableObject` 特别适合放这些内容：

- 敌人属性
- 技能参数
- 武器数值
- 掉落配置
- 关卡配置
- UI 的静态资源引用

它的价值不是“看起来高级”，而是：

- 配置可以在 Inspector 里直接改
- 同一份配置可以被多个对象复用
- 设计和调数不用反复改代码
- 数据和逻辑天然分离

### 示例：敌人配置和敌人实例

```csharp
using UnityEngine;

// 敌人配置，方便在 Inspector 中调整同类敌人的参数
[CreateAssetMenu(menuName = "Game/Enemy Config")]
public class EnemyConfig : ScriptableObject
{
    public string enemyName;
    public int maxHealth = 50;
    public float moveSpeed = 2f;
    public int damage = 10;
}

// 敌人实例只保存运行时状态，不直接修改配置资产
public class EnemyController : MonoBehaviour
{
    private EnemyConfig config;
    private int currentHealth;

    public void Initialize(EnemyConfig enemyConfig)
    {
        config = enemyConfig;
        currentHealth = config.maxHealth;
    }

    public void TakeDamage(int damage)
    {
        currentHealth -= damage;
        currentHealth = Mathf.Max(0, currentHealth);

        if (currentHealth == 0)
        {
            Die();
        }
    }

    private void Die()
    {
        Debug.Log($"{config.enemyName} 死亡");
    }
}
```

### 这里最容易犯的错

不要把运行时数据直接写回配置资产里。

比如这些字段不应该放进 `EnemyConfig`：

- 当前血量
- 当前坐标
- 当前是否死亡
- 当前状态机状态

这些东西都是“这一只敌人当前这一局的状态”，不是配置。

### 练习要求

做一个敌人配置系统：

- 用 `EnemyConfig` 配置数值
- 用 `EnemyController.Initialize` 初始化敌人
- 不要把血量写在配置里
- 同类敌人可以共用同一份配置

## 四、场景流程：不要让每个脚本都自己切场景

很多项目一开始会把场景切换写得很散：

- 开始按钮直接 `LoadScene`
- 死亡逻辑里直接 `LoadScene`
- 结算逻辑里直接 `LoadScene`
- 某个 UI 面板里也直接 `LoadScene`

这样后面会越来越乱。

更好的做法是：

- 统一由一个场景流服务管理切换
- 启动场景只负责启动
- 游戏场景只负责内容
- 菜单、加载、结算各自清楚

### 推荐流程

- `Boot` 场景：初始化全局服务
- `MainMenu` 场景：主菜单
- `Game` 场景：核心玩法
- `Result` 场景：结算界面

### 示例：异步场景加载

```csharp
using System;
using System.Collections;
using UnityEngine;
using UnityEngine.SceneManagement;

// 场景流控制器，统一处理异步加载与切换
public class SceneFlow : MonoBehaviour
{
    public IEnumerator LoadSceneAsync(string sceneName, Action<float> onProgress = null)
    {
        AsyncOperation operation = SceneManager.LoadSceneAsync(sceneName);

        while (!operation.isDone)
        {
            // 进度值通常到 0.9 之前会停住，这里做一次归一化
            float progress = Mathf.Clamp01(operation.progress / 0.9f);
            onProgress?.Invoke(progress);
            yield return null;
        }
    }
}
```

### 这一节要记住的原则

- 场景切换逻辑尽量集中
- 只有真正长寿命的服务才考虑常驻
- 不要让每个系统都变成全局常驻对象
- 场景应该承载内容，不应该承载全部业务核心

### 练习要求

做一个最简单的流程：

- 主菜单按钮进入游戏场景
- 游戏场景可以返回主菜单
- 场景切换时显示加载进度
- 不要在很多地方直接写 `SceneManager.LoadScene`

## 五、存档系统：把进度保存成数据

第三阶段开始，项目不再只是“这一局能玩”，而是要考虑：

- 玩家退出后能不能继续
- 进度能不能保存
- 配置变更后旧存档怎么处理
- 游戏关闭后状态能不能恢复

这时要再次强调：

> 能调的放配置，能跑的放运行时，能存的放存档。

### 示例：存档数据和存档系统

```csharp
using System.IO;
using UnityEngine;

// 存档数据，只保存能够落盘的字段
[System.Serializable]
public class SaveData
{
    public int version = 1;
    public int coin;
    public int health;
    public string currentScene;
}

// 存档系统，负责写入和读取本地文件
public static class SaveSystem
{
    private const string FileName = "save.json";

    private static string SavePath => Path.Combine(Application.persistentDataPath, FileName);

    public static void Save(SaveData data)
    {
        string json = JsonUtility.ToJson(data, true);
        File.WriteAllText(SavePath, json);
    }

    public static SaveData Load()
    {
        if (!File.Exists(SavePath))
        {
            return new SaveData();
        }

        string json = File.ReadAllText(SavePath);
        return JsonUtility.FromJson<SaveData>(json);
    }
}
```

### 存档系统要注意什么

- 存档结构尽量简单
- 版本号最好提前加上
- 不要把复杂引用直接写进存档里
- 不要把 `ScriptableObject` 当作存档容器
- 保存和读取最好由单独服务统一管理

### 练习要求

做一个最小存档功能：

- 保存金币和血量
- 退出后重新进入还能读回来
- 存档格式用独立数据类
- 不要直接保存场景对象引用

## 六、UI 架构：视图只负责显示

第二阶段已经知道 UI 可以通过事件刷新。第三阶段要进一步明确：

> UI 只负责显示和交互，不负责游戏规则。

当 UI 开始直接改血量、改金币、改背包、改关卡流程的时候，后面会很难维护。

更稳的方式是：

- 数据变化后通知 UI
- UI 只订阅，不主动计算核心规则
- 面板管理集中处理打开、关闭、层级

### 示例：金币面板绑定运行时状态

```csharp
using TMPro;
using UnityEngine;

// 金币面板只负责显示，不直接改动游戏数据
public class CoinView : MonoBehaviour
{
    [SerializeField] private TMP_Text coinText;
    private GameState gameState;

    public void Bind(GameState state)
    {
        gameState = state;
        gameState.OnCoinChanged += Refresh;
        Refresh(gameState.Coin);
    }

    private void OnDisable()
    {
        if (gameState != null)
        {
            gameState.OnCoinChanged -= Refresh;
        }
    }

    private void Refresh(int coin)
    {
        coinText.text = coin.ToString();
    }
}
```

### UI 这一层常见的拆法

- `UIRoot`：统一根节点
- `UIManager`：管理面板打开和关闭
- `BasePanel`：所有面板的公共基类
- `View`：只做显示
- `Presenter` 或绑定层：负责把数据传给视图

### 练习要求

做一个 UI 面板系统：

- 金币、血量、暂停面板都能显示
- UI 不直接去读一堆散落的对象
- UI 只订阅数据变化
- 面板打开和关闭集中管理

## 七、资源管理：把引用集中起来

当项目变大以后，最容易乱的不是代码，而是资源引用。

常见问题：

- 预制体到处拖
- 场景里挂了很多重复引用
- 资源路径写死在多个脚本里
- 一个资源改名后很多地方都要跟着改

第三阶段建议先做到一件事：

> 让资源引用集中，不要散落在各个脚本里。

### 示例：统一管理预制体引用

```csharp
using UnityEngine;

// 资源引用集中管理，避免预制体散落在各个脚本里
[CreateAssetMenu(menuName = "Game/Prefab Library")]
public class PrefabLibrary : ScriptableObject
{
    public GameObject hitEffectPrefab;
    public GameObject damagePopupPrefab;
}

// 特效生成器只从统一入口取资源
public class EffectSpawner : MonoBehaviour
{
    [SerializeField] private PrefabLibrary prefabLibrary;

    public void SpawnHitEffect(Vector3 position)
    {
        if (prefabLibrary == null || prefabLibrary.hitEffectPrefab == null)
        {
            return;
        }

        Instantiate(prefabLibrary.hitEffectPrefab, position, Quaternion.identity);
    }
}
```

### 资源管理的实际原则

- 先集中引用，再考虑优化
- 高频对象继续用对象池
- 低频对象可以直接实例化
- 大型项目再进一步考虑更完整的异步资源系统
- 不要让资源路径到处乱写

### 练习要求

做一个资源引用整理：

- 把特效、弹窗、界面预制体集中到一个地方
- 统一由生成器或工厂出口创建
- 不要让每个脚本自己保存一份资源引用

## 八、性能优化：先定位，再优化

第三阶段常见的误区是“感觉卡了就开始乱改”。

正确顺序应该是：

1. 先用工具看问题在哪
2. 再确认是真的热点
3. 最后只优化那部分

不要一上来就把所有代码都改成“看起来更高级”的写法。

### 常见的基础优化点

- 缓存组件引用
- 少做每帧重复查找
- 减少频繁分配临时对象
- UI 不要每帧刷新
- 合理使用对象池
- 减少无意义的 `Update`
- 把重逻辑拆开，避免所有东西每帧都跑

### 示例：缓存引用和打性能点

```csharp
using UnityEngine;
using UnityEngine.Profiling;

// 示例：缓存引用并给关键逻辑打点
public class EnemyMover : MonoBehaviour
{
    private Transform cachedTransform;

    private void Awake()
    {
        // 缓存 Transform，减少重复访问
        cachedTransform = transform;
    }

    private void Update()
    {
        Profiler.BeginSample("EnemyMover.Update");

        cachedTransform.position += Vector3.forward * 2f * Time.deltaTime;

        Profiler.EndSample();
    }
}
```

### 这里要养成的习惯

- 先看 Profiler
- 先看逻辑有没有重复
- 先看是不是 UI 刷新过多
- 先看是不是对象创建太频繁
- 不要凭感觉改代码

### 练习要求

给自己的 Demo 做一次排查：

- 找出一个每帧运行的重逻辑
- 给它加缓存或拆分
- 看看是否能明显减少重复计算

## 九、编辑器工具：把重复劳动交给工具

当项目开始有一定规模后，手工操作会越来越累：

- 手工创建配置
- 手工检查引用
- 手工生成默认数据
- 手工改一堆重复项

这时就值得开始做一些编辑器工具。

### 示例：一键创建默认游戏配置

```csharp
#if UNITY_EDITOR
using UnityEditor;
using UnityEngine;

// 一键创建默认游戏配置，减少重复手工操作
public static class GameConfigCreator
{
    [MenuItem("Tools/Project/Create Default Game Config")]
    public static void CreateDefaultGameConfig()
    {
        const string folderPath = "Assets/GameData";
        const string assetPath = "Assets/GameData/GameConfig.asset";

        if (!AssetDatabase.IsValidFolder(folderPath))
        {
            AssetDatabase.CreateFolder("Assets", "GameData");
        }

        GameConfig config = ScriptableObject.CreateInstance<GameConfig>();
        string uniquePath = AssetDatabase.GenerateUniqueAssetPath(assetPath);
        AssetDatabase.CreateAsset(config, uniquePath);
        AssetDatabase.SaveAssets();
        Selection.activeObject = config;
    }
}
#endif
```

### 编辑器工具适合做什么

- 创建默认配置
- 校验缺失引用
- 批量改名
- 批量生成数据
- 检查场景或资源规范

### 练习要求

做一个最小工具：

- 一键创建一个配置资产
- 一键检查某些字段是否为空
- 不要每次都靠手工复制粘贴

## 十、推荐实践项目：小型战斗原型

第三阶段最适合做的不是大而全项目，而是一个结构清楚的小型原型。

推荐做一个“战斗小沙盒”或“小型动作游戏原型”。

### 功能范围

- 一个玩家
- 两种敌人
- 一套技能系统
- 血量和金币 UI
- 场景切换
- 存档系统
- 资源引用管理
- 基础对象池
- 编辑器工具

### 这个项目里应该体现出的结构

- `ScriptableObject` 管配置
- `GameState` 管运行时数据
- `SaveData` 管持久化数据
- `SceneFlow` 管场景切换
- `UI` 只管显示
- `Services` 只管服务
- `Editor` 只管工具

### 推荐目标

做到下面这些，就算第三阶段开始真正落地了：

- 新增一个敌人，主要改配置，不大改代码
- 新增一个 UI 面板，不影响别的面板
- 新增一个存档字段，能清楚知道改哪里
- 新增一个场景，流程不需要重写
- 新增一个资源引用，不需要到处找脚本

## 十二、判断自己有没有真正进入第三阶段

不要只看自己“会不会写代码”，要看自己能不能把项目组织好。

可以用这些问题检查自己：

1. 我能不能清楚区分配置、运行时数据和存档数据？
2. 我能不能给项目设计一个不乱的目录和分层？
3. 我能不能让 UI 只负责显示，不直接改业务规则？
4. 我能不能把场景切换集中到一个流程里？
5. 我能不能让新增内容主要通过配置扩展，而不是到处改旧代码？
6. 我能不能用 Profiler 和日志定位问题，而不是靠猜？
7. 我能不能做一个能提升效率的小工具？

如果这几条能做到大部分，说明你已经开始真正进入第三阶段。

---

## 十三、最重要的提醒

第三阶段最容易犯的错不是“不知道怎么写”，而是“想一次把所有架构都做完”。

真正有价值的做法是：

- 先让项目清楚地跑起来
- 再把最容易混乱的边界拆开
- 再把重复劳动交给工具
- 再根据真实问题做优化

好的工程不是“用了很多复杂设计”，而是：

- 职责清楚
- 依赖简单
- 数据明确
- 流程可控
- 扩展时不容易炸

如果一个功能几十行代码就已经很清楚，就不要为了架构而架构。

第三阶段真正要练的是：

> 先把项目搭稳，再把它做得能长期迭代。
